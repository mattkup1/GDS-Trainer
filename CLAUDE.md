# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

**GDS Trainer** — a GDS (Global Distribution System) terminal simulator branded independently of any real GDS vendor. Two editions, both built on the same shared rules core (see below): a browser edition, plain HTML/CSS/JS split across `web/index.html` (markup), `web/style.css` (CRT/terminal styling), and `web/script.js` (all logic); and a Python terminal (CLI) edition, `gds-trainer-cli/`. It emulates the classic green-phosphor CRT terminal and industry-standard GDS entry mnemonics — historically associated with systems like Sabre — for training/educational purposes (sign-in, availability, sell, PNR build, end transaction). All flight/availability data is synthetic, generated by a seeded PRNG — there are no network calls or external dependencies anywhere in either edition.

Note: code comments and inline documentation below still refer to "Sabre" where they describe the real-world entry conventions this simulator is modeled on (e.g. "matches real Sabre's ticketing gate") — that's accurate engineering context, not product branding. The product's own name, UI text, and packaging use "GDS Trainer" throughout.

## Repo layout

- `web/` — the browser edition: `index.html` (markup), `style.css` (CRT/terminal styling), `script.js` (all logic), and `web/generated/` (`.js` wrapper files generated from `spec/*.json` for the browser to `<script src>` — regenerate with `python3 spec/build.py`, see below — don't hand-edit these; nothing else in this project reads `web/generated/`, only `web/index.html`).
- `gds-trainer-cli/` — the Python CLI edition (`gds_trainer/` package).
- `spec/` — the shared rules core both editions consume (command grammar, reference data, PNR-completeness rules, airport data) — see `spec/README.md`. Sibling to both edition folders, not nested in either, since both read it.
- `docs/` — user-facing documentation: `HOW-TO-BOOK-A-FLIGHT.md` (step-by-step walkthrough) and `GDS-TRAINER-BOOKING-GUIDE.html`/`.pdf` (the same walkthrough as a printable guide — the `.html` is the editable source, the `.pdf` is a build artifact).
- `tests/` — cross-edition test suite (shared scenarios run against both editions) — see `tests/README.md` and the Testing section below. Sibling to both edition folders, like `spec/`, since it tests both.
- `.github/workflows/` — CI (see Testing section below).
- `notes` — a symlink to an Obsidian vault; see the Obsidian integration section below.

`docs/GDS-TRAINER-BOOKING-GUIDE.pdf` is generated from `docs/GDS-TRAINER-BOOKING-GUIDE.html`. To update the guide: edit `docs/HOW-TO-BOOK-A-FLIGHT.md` first, port the same changes into `docs/GDS-TRAINER-BOOKING-GUIDE.html`, then regenerate the PDF with headless Chrome:

```bash
cd docs && "/Applications/Google Chrome.app/Contents/MacOS/Google Chrome" \
  --headless --disable-gpu --no-pdf-header-footer \
  --print-to-pdf="GDS-TRAINER-BOOKING-GUIDE.pdf" --print-to-pdf-no-header \
  "file://$(pwd)/GDS-TRAINER-BOOKING-GUIDE.html"
```

## Running it

There is no build step or package manager for the web edition — these are static files loaded via plain `<link>`/`<script src>` tags (not ES modules), so `web/index.html` can be opened directly via `file://` with no local server needed. (`spec/build.py` is the one exception — it's a content-authoring step for `spec/`, not an app build step; the app itself never needs it run to work, only to pick up a `spec/` edit.)

## Testing

```bash
cd gds-trainer-cli && pip install -e ".[dev]"   # once, pulls in pytest
source gds-trainer-cli/.venv/bin/activate
pytest                                          # everything, from repo root
```

Two layers, see `tests/README.md` for the full breakdown:
- `gds-trainer-cli/tests/` — fast Python-only unit tests for the CLI's pure-logic internals (`rng.py`, `dates.py`, `util.py`, a few `commands.py` helpers). No Chrome needed.
- `tests/` (top-level) — the shared cross-edition scenario suite (`tests/scenarios.py`): the same command sequences and structural expectations run against **both** editions — the CLI directly via `process_command`, and the browser via a real headless Chrome driven over the DevTools Protocol (`tests/cdp.py`, stdlib-only, no Node/selenium/playwright). This is what actually enforces that the two editions stay behaviorally in sync, the way `spec/` enforces it for the data/grammar they consume — see `tests/README.md` for why assertions are structural (message substrings) rather than exact fare/seat/ticket values.

**CI**: `.github/workflows/tests.yml` runs the full suite (`pytest` from repo root) on every push to `main` and every pull request, on `ubuntu-latest`. GitHub-hosted runners are Linux, so `tests/cdp.py`'s Chrome discovery doesn't use the macOS path there — the workflow provisions Chrome via `browser-actions/setup-chrome` and points `tests/cdp.py` at it through the `GDS_TRAINER_TEST_CHROME` env var (`default_chrome_path()` in `tests/cdp.py` checks that env var first, then the macOS install path, then common Linux binary names on `PATH` — same override works for local Linux dev, not just CI).

## Shared rules core (`spec/`)

The command grammar, reference data (SSR codes, card types, fare-formula constants, etc.), airline data, airport data, and PNR-completeness rules are **not** independently hand-maintained in `web/script.js` and `gds-trainer-cli/` — both editions consume the same canonical files in `spec/` (`spec/README.md` has the full breakdown). Edit `spec/*.json`, not the generated copies:

- Python (`gds-trainer-cli/gds_trainer/`) loads `spec/*.json` directly at runtime — no build step.
- The browser can't `fetch()` local JSON from `file://` (Chrome CORS) and this project has no bundler, so it loads generated `.js` wrapper files instead, from `web/generated/` (`reference-data.js`, `airlines.js`, `command-grammar.js`, `pnr-completeness.js`, `airports.js`, all `<script src>`'d in `web/index.html` before `script.js`). **After editing anything in `spec/`, regenerate them with `python3 spec/build.py`** and commit the regenerated files — nothing does this automatically.
- Exception to "commit the regenerated files": `spec/airline-logos/` (real airline logo images, one per IATA code) and its generated output `web/generated/airline-logos.js` (the images base64-inlined as data URIs) are both gitignored — real airline logos are trademarked/copyrighted third-party assets this repo doesn't distribute, unlike the plain-text airline codes/names in `spec/airlines.json`. See `spec/airline-logos/README.md`. Missing/never-added logos just mean the browser falls back to a generated colored-badge placeholder (`airlineBadgeSVG`/`airlineLogoHTML` in `web/script.js`) for that carrier — this is expected on a fresh checkout, not a bug.

This exists because the alternative was proven costly in practice: before this split, a passenger-count validation rule and a phone-format error message were the same bug, fixed by hand in both codebases in one sitting. Adding a new command, SSR code, fare constant, or completeness rule now means editing `spec/`, not two dispatchers.

## Architecture (`web/script.js`)

Everything lives in one IIFE. Key pieces:

- **`state`** — the whole app's runtime state: `signedIn`/`sine`/`pcc`, `pnr` (the in-progress booking), `lastAvail` (most recent availability search results), `lastDisplay` (numbered element list from the last PNR render), `history` (saved PNRs keyed by record locator), and `cmdHistory` (for arrow-key recall in the input).

- **`processCommand(raw)`** — the command dispatcher. The signed-in/signed-out gate (checks `SI`/`HELP` before sign-in, otherwise falls through) is hardcoded here since it's structural, not a repeating pattern. Everything else — `SO`, availability (`A`/`1`), sell (`0...`), name field (incl. multi-passenger and lap-infant suffix), phone, received-from, pricing (`WP`/`WPNCS`), ticketing arrangement (`7TAW`/`7TAX`), form of payment, `TKTT`, SSR/OSI/FQTV (`3...`), seats (`4...`), airport encode/decode (`DC`/`DAN`), PNR management (`*R`/`*H`/`*{LOCATOR}`), cancel (`X{N}`/`XI`), `IG`/`ER`/`ET` — is driven by looping over `COMMAND_GRAMMAR` (loaded from `spec/command-grammar.json`, generated into `command-grammar.js`): an ordered list of `{name, pattern, handler}` entries, first match wins. **The ordering and exact regex for every command live in `spec/command-grammar.json`, not in this file** — check there before adding or reordering a command; both editions loop over the identical list so they can't drift out of sync. Each matched entry calls its `handler` token through the `HANDLERS` lookup table, which adapts the generic `(rawInput, ...captureGroups)` call shape to each named command-handler function (`genAvailability`, `sellFromAvail`, `handleName`, `addFopCreditCard`, etc.).

- **Pricing (`priceItinerary` / `WP` / `WPNCS`)** — mimics Sabre's fare-quote entry. Requires at least one segment and one name on the PNR; deterministically derives a base fare (seeded by segment details, same seeding pattern as `genAvailability`), a handful of itemized taxes, and a total, then stores it on `state.pnr.pricing`. The formula's tunable constants (base fare coefficient, distance range, tax count/amount ranges) live in `spec/reference-data.json`'s `fareFormula` — the algorithm itself (multiply/round/accumulate against the seeded RNG) is separate parallel code in each edition, only the numbers are shared. Selling or cancelling a segment invalidates any stored price (`invalidatePricing`/`removeElement`), matching real Sabre where itinerary changes stale out a fare quote — it must be re-priced with `WP` before ticketing. `endTransaction` treats a missing `p.pricing` as an incomplete-PNR error, same as a missing name or ticketing arrangement (see the PNR-completeness bullet below).

- **Baggage allowance (`formatBaggagePieces`/`_format_baggage_pieces`, `spec/reference-data.json`'s `baggageAllowance`)** — real Sabre fare quotes and itinerary documents always carry a checked-bag allowance alongside the fare rules (change fee/refundable/advance purchase), keyed off the booking class the same way fare rules are; this was previously entirely absent, meaning a lap infant wasn't the only thing that flew "free" in this simulator — nobody's checked bags were priced or disclosed at all. `baggageAllowance.pieces` (`spec/reference-data.json`) maps each booking class to a free-checked-bag count (3 for `F` down to 0 for `M`, matching real deep-discount "basic economy" fares carrying no free checked bag), with a single shared `weightLimitLbs` (50, ~23kg) since this trainer doesn't model per-fare weight tiers. Surfaced everywhere fare rules already are, reusing the exact same "keyed off `p.segments[0].cls`, single value for the whole itinerary" simplification `priceItinerary`/`price_itinerary` already uses for `fareBasis`/`rules`: `WP`'s fare-rules block, `FQ{ORIG}{DEST}/{CLASS}`'s stand-alone fare-rules lookup, and the `EM`/`EMI`/`EMT` itinerary document's fare-summary section (it rides along for free there since `p.pricing`/`p["pricing"]` is copied into the document wholesale, same as every other pricing field). Purely informational — no completeness rule, no booking-time enforcement; real Sabre doesn't gate ticketing on baggage either, it's disclosure only.

- **Availability generation (`genAvailability`)** — flight data is deterministically pseudo-random: `hashStr()` seeds `mulberry32()` from the route+date string, so the same query always returns the same flights. There is no real airline/schedule data source; adding one would mean replacing this function's internals, not the dispatcher. Every displayed line is one ordinary flight (`genFlight`/`_gen_flight`), each carrying its own `orig`/`dest` — matching real Sabre, where a connection is never a system-bundled multi-leg line: each leg of a workable connection is shown as its own separately-numbered line with its own city pair (the `RTE` column), and the display gives no hint which lines connect. Generation always produces the existing 5-8 nonstops first (`orig`/`dest` matching the search), then **always appends exactly 2 workable connections as 4 more lines** (2 legs each — a via-airport picked from `AIRPORTS`, with a layover generated to always clear whatever minimum connect time (MCT) applies to that specific via-airport, see below), continuing to draw from the same RNG stream — this keeps line 1 deterministically a nonstop for every route/date (so nothing that already sells "line 1" needs to know connections exist) while guaranteeing every search has at least one sellable connection. `sellFromAvail`/`sell_from_avail` (`0{LINE}{CLASS}{SEATS}`) sells a single line as before, unaffected. `sellConnection`/`sell_connection` (`0{SEATS}{CLASS1}{LINE1}{CLASS2}{LINE2}`, e.g. `02Y1M2` — real Sabre's actual connection-sell entry) looks up both referenced lines, validates the first's `dest` matches the second's `orig` and the connection meets minimum connect time (`requiredMct`/`_required_mct`, spec/reference-data.json's `minimumConnectTime`: a real GDS's actual MCT table is keyed per specific airport/terminal, which this app has no data for, so this uses the same domestic/international default a real GDS itself falls back to when no airport-specific override exists — 45 min if both legs stay within the connecting airport's country, 90 min if either leg crosses a border, derived from each airport's country in `spec/airports.json`) before validating each leg's requested class/seat count (so a shortfall on leg 2, or mismatched cities, never leaves the PNR half-sold), then pushes one ordinary single-leg segment per leg, tagged with a shared `marriedGroup` id (a monotonic counter, `state.nextMarriedGroupId`/`STATE.next_married_group_id` — not the segment's array index, which could collide with an unrelated later marriage after intervening cancels shrink and regrow the array) — a connection is purely an availability/sell-time concept; once sold it's indistinguishable from two independently-sold nonstop segments for pricing, seat maps, ticketing, and the itinerary document, all of which handle it automatically with no changes. The one exception is cancellation: `marriedPartnerIndices`/`married_partner_indices` (used by `buildElements`/`build_elements`, which appends a `MARRIED TO SEG{n}` note to each married segment's displayed line, and by `cancelElements`/`cancel_elements`, which blocks a cancel that names only *some* of a married group's currently-displayed element numbers — `UNABLE TO CANCEL - ... CANCEL BOTH TOGETHER (X{n},{m})` — rather than silently orphaning the other leg) is the only place a connection's married legs are still treated as linked after the sell. `XI` and `SP` (divide) need no special handling: `XI` already clears every segment unconditionally, and divide already deep-copies `segments` verbatim, so a `marriedGroup` tag just copies along correctly.

- **Codeshare flights (`genFlight`/`_gen_flight`, `spec/reference-data.json`'s `codeshare`)** — real availability regularly shows a flight marketed by one carrier but operated by another; without it, this simulator's flight identity was always a single, unified carrier+number, unlike a real display. Whether a generated flight is a codeshare (and if so, its operating carrier/flight number) is derived from a **separate** `mulberry32(hashStr('CS'+airline+flightNum+orig+dest+dep))` instance keyed off the flight's own already-generated identity fields — deliberately *not* additional draws from the `rng` parameter `genFlight`/`_gen_flight` shares with every other flight in the same search. Consuming from the shared stream would shift every subsequent draw (and therefore every flight generated afterward), silently invalidating the large body of existing tests that hardcode specific flight/seat/connection facts per route+date (see `tests/scenarios.py`'s "empirically confirmed" comments) — the derived-seed approach adds the feature with zero risk of that cascade, confirmed by the full suite passing unchanged before any codeshare-specific assertions were added. Surfaced everywhere a flight or segment is displayed: availability and schedule display (an indented `OPERATED BY {NAME} ({CODE}{NUM})` line under the flight), and `formatSegmentShort`/`format_segment_short` (an appended `OPR BY {CODE}{NUM}`) — the latter is the single shared formatter behind sell confirmations, the activity log, the PNR display, the pricing summary, and cancelled/changed/cleared lists, so one change propagates everywhere, plus the itinerary document's per-segment card. `sellFromAvail`/`sell_from_avail` and `sellConnection`/`sell_connection` copy the operating-carrier fields onto the sold segment; `directSell`/`long_sell` (hand-typed, no generated flight to derive one from) and ticketing's validating-carrier logic (`segments[0].airline`, already the marketing carrier — the correct real-world choice) need no change.

- **Overnight arrivals (`formatArrival`/`format_arrival`, `dates.py`/`minutesToClock`'s neighbor)** — real Sabre marks an arrival landing on a different calendar day than its departure with a `+N` suffix (e.g. `1206A+1`) rather than a bare same-day clock time; without it a red-eye/long-haul flight (duration can already push `arr` past 1440 minutes for a late-enough `dep`) looks like it arrives before it departs. Computed as a diff of whole-day counts between the raw `dep`/`arr` minute values (`arr // 1440 - dep // 1440`, not just "does `arr` exceed 1440") — genuinely relative, so it stays correct even after `applyScheduleChanges` shifts both by an identical delta, without needing to touch `dinfo` at all. Threaded through every place an arrival time is printed: availability (`ARR` column, widened to fit the suffix), schedule display (same), `formatSegmentShort`/`format_segment_short` (used by the PNR display and activity log), the itinerary document (both editions), and the schedule-change log line. `minutesToClock`/`minutes_to_clock` itself is unchanged — still just the bare clock-time formatter, used as-is for every `dep` (which needs no suffix relative to itself).

- **Schedule display (`S{DDMMM}{ORIG}{DEST}`, `genSchedule`/`gen_schedule`)** — real Sabre's schedule entry is the identical shape as a city-pair availability entry, just with `S` in place of `A`/`1` (confirmed: "the entries to display air schedules are identical to CPA entries, except the letter 'S' is used"); it answers "what flies this route" across a several-day window, independent of booking classes/seat counts, rather than "what's sellable on one date." Shows the queried date plus the following 6 days (7 total), one block per date. Deliberately **reuses `genAvailability`'s exact per-date seed and generation** (`hashStr(orig+dest+day+mon+year)` → `mulberry32` → the same nonstop-count formula and `genFlight`/`_gen_flight` calls) once per date in the window, rather than a second, disconnected formula — so for whichever date in the window is also covered by an `A`/`1` search on the same route, the schedule shows the literal same flights (same airline/flight number/times/equipment), just without the class/seat columns, reinforcing that it's the same underlying schedule, only a different view. Nonstop only (no connections — those are an availability/booking-time concept, not a schedule-lookup one). Purely a read-only lookup like `DC`/`DAN`/`FQ`: no PNR interaction, no completeness rule.

- **PNR element model (`buildElements` / `refreshAndPrintPNR` / `cancelElements`)** — names, infants, segments, seats, SSRs, OSIs, pricing, phones, receivedFrom, and ticketing are stored on `state.pnr` (names/segments/phones/infants/seats/ssrs/osis as arrays, the rest as single values), but flattened into a single numbered list every time the PNR is displayed. `state.lastDisplay` holds that numbering, and `X{n}` (or a range/list of `n`s, or `XI` for the whole itinerary) cancellation looks up the array/index each number points to — so cancellation only works correctly against the most recently displayed numbering, not stale state. Multi-element cancels process highest-numbered element first so earlier splices don't shift the indices of elements still queued for removal. Seats are linked to segments by array index (`seat.segIdx`); cancelling a segment (`removeElement`'s `'segment'` branch, and `cancelItinerary` for `XI`) drops that segment's seats and reindexes the rest so they still point at the correct remaining segment.

- **Seat maps (`getSeatMap` / `showSeatMap` / `assignSeat`)** — like availability and pricing, the occupied/open grid is deterministic: seeded by the segment's flight+date+route, so `4{N}` always regenerates the same layout for that segment. The layout itself (row count and column groups, e.g. 2-2 for a regional jet, 3-3 for a narrowbody, 3-3-3 for a widebody) is keyed off the segment's `equip` code via `spec/reference-data.json`'s `seatLayouts` (falling back to `_default`, 3-3/30 rows, for any unrecognized code) — it is **not** a fixed 6-column grid. Double-decker aircraft (747-400/-8 `744`/`748`, A380 `388`) use a `decks` array instead of a flat `rows`/`cols` pair — each deck (`UPPER DECK`/`MAIN DECK`) has its own `rowStart`, row count, and column groups, with row numbers unique/contiguous across decks (upper deck ends where main deck begins) so a bare row number is enough to resolve which deck it's on. `layoutDecks`/`layout_decks` normalizes every layout (single- or multi-deck) into this same deck-list shape, so `getSeatMap`/`get_seat_map`, `assignSeat`/`assign_seat`, and the rendering code below only ever handle one shape. `showSeatMap`/`show_seat_map` build the header and each row from the same per-cell template function so they can't drift out of alignment with each other, printing one header/body block per deck (with a deck-label line first when the aircraft has more than one). `assignSeat`/`assign_seat` validate the row against the matching deck's range and the seat letter against that deck's specific column groups (rejecting e.g. `14F` on a 2-2 aircraft, or a valid main-deck-only letter on an upper-deck row), not against a hardcoded `A-F`. Assignments are only checked against this generated grid and the PNR's own `state.pnr.seats`, not against other passengers' bookings (there's no shared inventory across simulated PNRs). Each seat entry is optionally tied to a passenger via `4{N}-{SEAT}/{PAX#}` (`assignSeat`/`assign_seat`), the same `-{PAX#}` convention as a regular SSR — validated the same way (`INVALID PASSENGER NUMBER`), and reprinted the same way (`PAX {n} ({name})` appended to the confirmation and the PNR display line). The passenger number is optional only when it's unambiguous: exactly one name on file defaults to that passenger automatically (so a solo booking's `4{N}-{SEAT}` keeps working unchanged), but two or more names on file require it explicitly (`MULTIPLE PASSENGERS ON FILE - SPECIFY PASSENGER NUMBER`) rather than silently leaving the assignment unattributed — an unattributed seat has no way to follow the right passenger through a later `dividePnr`/`divide_pnr` (see below), so this pushes attribution to happen at assignment time instead. The browser edition additionally renders a clickable seat-map grid (`renderSeatMapPanel`, browser-only) inside the dock's SEAT MAP tab (see below) alongside the ASCII map — one section per deck, each with its own header — clicking an open seat types and submits the real `4{N}-{SEAT}` command via `submitCommand()` rather than mutating state directly, matching `notes/GUI Expansion Scope-Out.md`'s constraint that GUI affordances never bypass the command dispatcher.
- **Persistent dock + toolbar (browser-only GUI chrome)** — `web/index.html`'s `#housing` wraps `#crt` (the terminal) and a new `#dock` sidebar inside a `#mainrow` flex row (stacks below the terminal under 900px width via a media query). The dock is a four-tab panel (`#dockTabs`, a 2x2 grid of buttons), data-driven via a `DOCK_TABS` lookup table (`web/script.js`) mapping each tab key to its button/panel pair so `switchDockTab(tab)` is one loop rather than a parallel if-chain per tab:
  - **PNR tab** (`#dockPnrTab`) mirrors `state.lastDisplay`/sign-in status live via `renderPnrPanel()`. It's called from `refreshAndPrintPNR()` (covers most mutating commands automatically) plus four explicit call sites that reset `state.pnr`/`state.lastDisplay` without going through it: `endTransaction()`'s `ET` branch, `queueEnqueue()`, `ignorePnr()` (`IG`), and `boot()`/sign-in/sign-out — otherwise the dock would show stale content after those resets, unlike the terminal (which is append-only text and never claimed to reflect "now").
  - **SEAT MAP tab** — the same `#seatMapPanel` element from the seat-map feature above, just re-parented into the dock and switched to via `switchDockTab('seat')` instead of floating as its own modal.
  - **ENCODE/DECODE tab** (`#lookupPanel`, modeled on real Sabre Red's "Encode/Decode" sidebar tool) — live search-as-you-type over the same `AIRPORTS`/`AIRLINES` data `DC`/`DAN` already read, ranked so an exact/prefix code match always outranks an incidental substring hit elsewhere (`lookupMatchRank()` — searching `ORD` must surface Chicago O'Hare, not Alamogordo, whose city name merely contains "ord"). Airport rows are clickable and run the real `DC{code}` command via `submitCommand()`; this is safe under the "GUI must not offer a point-and-click alternative to typing the entry" rule below because `DC` is read-only and mutates no PNR state, unlike a booking action. Airline rows are display-only since no decode command exists for them.
  - **FORMAT FINDER tab** (`#formatsPanel`, modeled on real Sabre Red's "Format Finder" tool) — a filterable, category-grouped reference over `COMMAND_GRAMMAR` (`spec/command-grammar.json`) itself, driven by three additive metadata fields on each grammar entry (`category`/`desc`/`example`) that the dispatcher loop ignores — grouping is done by collecting into a category map rather than scanning for streaks, since a category's entries aren't necessarily contiguous in the grammar's dispatch-order array (e.g. `PNR BUILD` and `TICKETING` interleave) and that array's order must stay untouched (`spec/README.md`: "first match wins"). Clicking a result only inserts its `example` into `#cmdline` and focuses it — it never submits, per the guiding constraint in `notes/GUI Expansion Scope-Out.md` that GUI affordances must not become a point-and-click alternative to typing a PNR-mutating entry.

  A `PANEL` toggle button hides/shows the whole dock, persisted via the existing settings `localStorage` mechanism (`DEFAULT_SETTINGS.dockVisible`) alongside the theme/glow/scanline settings. The toolbar's old cluster of zero-argument quick-action buttons (`SIGN IN`/`SIGN OUT`/`DISPLAY PNR`/`PRICE (WP)`/`END TRANSACT`/`HELP`) was removed — real GDS terminals don't offer command shortcuts as toolbar buttons, and the ENCODE/DECODE and FORMAT FINDER tabs are the actual real-GDS-modeled replacement for that space. This entire section is browser-edition only — the CLI edition has no GUI equivalent, per `notes/GUI Expansion Scope-Out.md`.

- **Special service requests / OSI (`SSR_CODES`, the `3...` dispatcher branches)** — SSR codes are validated against a fixed lookup table (meal requests, wheelchair, unaccompanied minor, etc.) loaded from `spec/reference-data.json`'s `ssrCodes`; unrecognized 4-letter codes after `3` are rejected rather than silently accepted. `3OSI{AL}{TEXT}` is checked ahead of the general `3{CODE}` pattern (in `spec/command-grammar.json`'s ordering) since `OSI` would otherwise also satisfy the 4-letter-code shape. `3FQTV{AL}{NUMBER}[-{PAX#}][/{TIER}]` has its own grammar entry (not the general `3{CODE}` one, since the shape differs) but follows the same `-{PAX#}` convention as a regular SSR — both the passenger number and the tier are independently optional, validated the same way `addSsr`/`add_ssr` validates its own `-{PAX#}`, and the resolved name (`PAX {n} ({name})`) is appended to the stored text the same way.

- **PNR completeness (`spec/pnr-completeness.json`)** — `endTransaction`/`end_transaction` and `issueTickets`/`issue_tickets` don't hardcode their own if-chains of required fields; both walk the same ordered `{field, check, message}` rule list (`end_transaction` and `issue_tickets` keys) via a small generic checker (`firstIncompleteMessage`/`_first_incomplete_message`) and print the first rule's message that fails. Add or reword a completeness check there, not in either dispatcher.

- **Group PNRs (`-{N}TBA/TBA`, `endTransaction`'s 10+-names gate)** — real groups (confirmed: "10+ passengers traveling together") are built with placeholder passengers literally named `TBA/TBA`, repeated rather than individually spelled out. The name field's leading count digit (`-{N}{SURNAME}/{GIVEN}...`) is captured but otherwise unused elsewhere (the real driver of how many names get added is how many `/`-separated given-name parts follow) — `handleName`/`handle_name` special-cases exactly `-{N}TBA/TBA` with `N > 1` to push `N` literal, unnumbered `"TBA/TBA"` names in one entry (matching the real convention: identical placeholders distinguished only by position in the name list, not synthesized unique strings), reusing the same party-size-vs-seats-sold guard every other name entry already uses. Real groups also need a deposit on file before saving — modeled with **zero new command code**: `"DEPS": "GROUP DEPOSIT RECEIVED"` is just another entry in `spec/reference-data.json`'s `ssrCodes`, handled entirely by the already-generic `3{CODE}` SSR path. `endTransaction`/`end_transaction` has one bespoke addition (conditional on party size, so not expressible as a single-field `spec/pnr-completeness.json` rule — same precedent as `dividePnr`'s "at least one passenger must remain" check): if `names.length >= 10` and no SSR has `code === 'DEPS'`, block with `PNR INCOMPLETE - GROUP DEPOSIT REQUIRED FOR 10+ PASSENGERS (ENTRY: 3DEPS)`. Finalizing a placeholder (replacing `TBA/TBA` with a real name closer to departure) needs **no new command at all** — `X{n}` cancels that specific `NM` element, then an ordinary `-{SURNAME}/{GIVEN} {TITLE}` entry adds the real name, exactly like editing any other name. The names/ticketing deadline is the existing `7TAW.../7TAX...` entry doing double duty — no second, unverified deadline mnemonic was invented for it.

- **Extra seat (`EXST`/`CBBG`/`STCR` SSR codes)** — real airlines let a passenger buy an additional seat (comfort/oversized-passenger purchase, or to hold a musical instrument/fragile item, or a medical stretcher case); the real-world mechanism is selling one more seat on the segment than there are passenger names, tagged with an SSR identifying why. This needed **zero new logic**, only three new `ssrCodes` entries in `spec/reference-data.json` (`EXST`/`CBBG`/`STCR`, same `DEPS` precedent above) — every piece it depends on already existed: `handleName`/`handle_name`'s party-size guard only ever blocked *more* names than seats sold, never fewer, so `01Y2` + a single `-SURNAME/GIVEN` name entry was already legal; `priceItinerary`/`price_itinerary` already multiplies each segment's base fare by that segment's own `seats` count (not `names.length`), so the extra seat is already priced for. One known, deliberate simplification: `issueTickets`/`issue_tickets` issues one ticket per *name* (plus one per infant) — it does not issue a separate ticket coupon for the extra seat itself, unlike some real airlines' practice of ticketing it under a companion record. Training value (booking, pricing, and SSR-tagging the extra seat correctly) is kept without adding a second passenger-like ticketing path for what isn't a real traveler.

- **Child fare (`(CHD)` name suffix, `state.pnr.children`/`STATE.pnr["children"]`)** — real GDS fares distinguish ADT/CNN/INF passenger types; this models the CNN case as a discount off the adult base fare (`fareFormula.childFareMultiplier`, `spec/reference-data.json`), distinct from a lap infant (which is free and isn't a named passenger at all - see below). A child is a fully named, seat-occupying passenger, so unlike the infant suffix (which is stripped off the *end of the whole entry* and creates a separate `infants` record), `(CHD)` attaches to one specific `/`-separated given-name token within a name entry - e.g. `-SMITH/JOHN MR/JOHNNY MSTR(CHD)` for one adult and one child sharing a surname - and only sets a fare-type flag (`{pax}`, the same 1-based passenger-index convention `docs`/`seats` already use) on the passenger that's already being added by the existing loop; no DOB is captured, since nothing here does age-based eligibility checking, just fare type. `priceItinerary`/`price_itinerary` treats the child count as constant across every segment (same "everyone travels the whole itinerary" simplification already used for baggage/fare rules), splits each segment's seats into child/adult counts capped at that segment's own seat count (so an unnamed extra seat - `EXST`/`CBBG`/`STCR` - can never accidentally price as a child fare, since it has no name to begin with), and prices each portion separately before summing. `buildElements`/`build_elements` appends `(CHD)` to the child's `NM` line the same way a married segment gets its `MARRIED TO SEG{n}` note - display-only, never written into the stored name string itself, since that string is reused verbatim elsewhere (SSR/seat `PAX {n} ({name})` attribution, ticket issuance, infant `adult` matching). `dividePnr`/`divide_pnr` reindexes `children` by pax exactly like `docs`/`seats` already do, so the tag correctly follows a divided-out child to their new PNR.

- **End transaction (`endTransaction`)** — validates the PNR is complete (segment, name, fare quote, phone, received-from, form of payment, ticketing all present, per `spec/pnr-completeness.json`) before generating a 6-character record locator via `genLocator()` and saving into `state.history`. `ER` keeps the PNR loaded and redisplays it; `ET` clears the work area for the next booking. Both behaviors matter for training accuracy — don't collapse them into one. **Cancelling a saved PNR entirely** (`XI`, or `X{n}` against every segment, then `ER`/`ET`) is a distinct bespoke path ahead of the normal completeness gate: once a PNR already has a `locator` and its `segments` array is empty, none of the standard fields (name, fare quote, phone, RF, FOP, ticketing) are meaningful for an itinerary that no longer exists, so `endTransaction` skips the whole gate and re-saves the PNR as-is under the same locator, printing `PNR CANCELLED - ALL ITINERARY SEGMENTS REMOVED` instead of the usual confirmation. Without this, the unconditional "segments non-empty" rule would permanently trap the cancellation in the work area — `IG` discards the edit but never touches `state.history`, so the old, still-itineraried snapshot would stay retrievable forever, which is wrong (a real GDS lets an agent cancel an entire booking and have that cancellation persist). Restricted to `ER`/`ET` only — a *brand-new* PNR (no locator yet) still correctly requires a segment, and `EM`/`EMI`/`EMT` still refuse an empty itinerary, since generating a customer document for a cancelled booking makes no sense.

- **Itinerary/invoice documents (`EM`/`EMI`/`EMT`, `endTransaction`)** — real Sabre's `EM`/`EMI`/`EMT` are end-transaction variants that also mail the passenger an itinerary/invoice/e-ticket document; this offline simulator has no real email, so the honest equivalent is generating a formatted, print-ready document instead — same completeness gate and work-area-clearing as `ET`, plus a document. `spec/reference-data.json`'s `emailDocuments` is the single source of truth both editions read for what each mode includes (`sections`: `passengers`/`segments`/`seats`/`ssrs`/`osis`/`pricing`/`formOfPayment`/`tickets`) and its customer-facing label — `EM` is itinerary-only, `EMI` adds the fare/payment breakdown (an "invoice"), `EMT` is ticket-focused (and explicitly notes `NOT YET TICKETED` if `TKTT` hasn't run, since `tickets` isn't part of `end_transaction` completeness). All three modes include `seats`/`ssrs`/`osis` — a chosen seat or a meal/wheelchair/FQTV request is part of what actually shipped on the itinerary regardless of which variant generated the document, so there's no principled reason to drop them from any one mode (this bit both `seats` and `ssrs`/`osis` for `EMT` specifically before it was fixed - check `sections` here first if a section seems to be silently missing from one mode's output). `segmentStatusLabels` translates the internal `HK`/`HL` codes to customer-readable text (`CONFIRMED`/`WAITLISTED`) for the document only — the ASCII/GUI displays elsewhere keep the raw agent-facing codes. In the browser, `buildItineraryDocument`/`renderItineraryDocumentHTML`/`openItineraryDocument` assemble the data, render one self-contained HTML string (all interpolated free-text fields go through `escapeHtml()` since it's written via `document.write()`), and open it in a new tab with a "Print / Save as PDF" button — zero new dependencies, matching this project's no-network/no-external-deps constraint. Each segment's carrier gets a badge via `airlineLogoHTML()`: a real logo (base64 data URI from `web/generated/airline-logos.js`, see the Shared rules core section above) if one was provided for that IATA code, otherwise a generated colored placeholder (`airlineBadgeSVG`) — never a relative-path `<img src>`, since the document is written into a blank `window.open('', '_blank')` target with no reliable base URL to resolve one against. The CLI edition (no browser, no PDF) has no GUI equivalent — `build_itinerary_document`/`print_itinerary_document` in `commands.py` render the same content as a formatted terminal block instead, same asymmetry pattern already documented for the browser-only seat-map/dock GUI.

- **Ticketing (`TKTT`, `issueTickets`)** — deliberately kept separate from `endTransaction`/completeness, matching real Sabre: a PNR can be saved (`ER`/`ET`) without being ticketed (deferred ticketing via a time limit is normal), and the `7TAW/`/`7TAX...` "ticketing arrangement" only sets a deadline — it doesn't ticket anything. `TKTT` is the actual ticket-issuance entry; it requires the PNR to already have a locator (i.e. already end-transacted once), a fare quote, a ticketing arrangement, and a form of payment, and refuses to double-ticket an already-ticketed PNR. It generates one ticket number per name (plus one per infant) using a real-world IATA airline numeric code (`AIRLINE_NUMERIC_CODES`) for the first segment's carrier as validating carrier, deterministically seeded by locator+passenger like the rest of the app's synthetic data. `invalidatePricing()` — already called whenever a segment is sold — also voids any issued tickets and announces it, and the segment/fare-quote cancellation paths in `removeElement`/`cancelItinerary` silently clear `state.pnr.tickets` the same way they silently null `pricing`, so a ticketed PNR whose itinerary changes always needs `WP` then `TKTT` again before it can be re-saved as ticketed.

- **Ticket void (`TKTV`) / refund (`TKTR`)** — the missing inverse of `TKTT`. Both are gated by their own `spec/pnr-completeness.json` rule (`tickets` non-empty) via the same generic checker `issue_tickets` already uses. `TKTV` only clears `tickets` — a void isn't an itinerary change, so `pricing`/`ticketing` stay valid and `TKTT` can reissue immediately. `TKTR` additionally checks `FARE_RULES[segments[0].cls].refundable` (the same `fareRules` data `priceItinerary` already reads) and blocks nonrefundable fares outright; on success it clears both `tickets` and `pricing` (a refund undoes the fare itself, not just the ticket), so the itinerary needs a fresh `WP` before it can be reticketed.

- **Ticket exchange (`WFR{TICKET#}`, `exchangeTicket`)** — real Sabre's `WFR` starts an exchange against an already-issued ticket, applying its value toward a newly re-priced itinerary and showing an additional collection (ADCOLL) or residual before reissuing; real Sabre's actual process is a heavier multi-step workflow (`WFR` → an auto-priced price-quote record → a separate reissue-commit entry) that this deliberately simplifies into one entry, keeping the training value (apply old value, show ADCOLL/residual, reissue) without simulating that machinery. This needed a real gap fixed first: nothing in the PNR model retained a "previous ticket/fare" once invalidated — `clearPricingAndTickets`/`_clear_pricing_and_tickets` is a new shared primitive (used by `invalidatePricing`, `removeElement`'s `'segment'`/`'fq'` branches, `cancelItinerary`, and the schedule-change mutation — every path that used to null `pricing`/`tickets` directly) that snapshots them into `priorTickets`/`priorPricing` first, but only when the PNR was actually *ticketed* (both set) — a priced-but-not-yet-ticketed PNR has nothing to exchange. `WFR` requires `priorTickets` non-empty and a fresh `pricing` (gated via `spec/pnr-completeness.json`'s `exchange_ticket` rule, same generic checker), looks up the given ticket number among `priorTickets`, computes `pricing.total - priorPricing.total`, reissues via the same per-name/per-infant loop `issueTickets` uses but with the old ticket number folded into `genTicketNumber`'s seed input (reusing the plain seed would regenerate the identical number), then clears the stash — a plain `TKTT` (choosing to reissue fresh instead of exchanging) clears it too, so a stale exchange opportunity never lingers. `refreshAndPrintPNR` prints a hint whenever a stash exists and pricing is fresh (ready to exchange), alongside the existing schedule-change alert (now mentioning `WFR` as the alternative to `TKTT`) — the two compose, since a schedule change is just one path into `priorTickets`.

- **PNR divide (`SP{N}` / `SP{N},{M}`, `dividePnr`)** — splits named passenger(s) out of the current PNR into a new, separately-locatored PNR. `names` (by array index), `docs` (an explicit `pax` index), and now seat *assignments* (`state.pnr.seats`' own `pax`, see the Seat maps bullet above) are all unambiguously per-passenger in this PNR model; `infants` link only by matching the adult's exact name string, and `ssrs` bake any pax number into free text only — so those don't move with a divided passenger. Moved: the name(s), any infant whose `adult` matches a removed name, any doc whose `pax` matches a removed index, and any seat whose `pax` matches a removed index — all three reindexed the same way (moved elements renumbered `1..N` against the new PNR's own name list, remaining elements' `pax` shifted down by however many removed indices fell before them, same pattern `removeElement`'s `'segment'` branch already uses for `seat.segIdx` after a cancel). A seat with no `pax` on file (unattributed - only possible on a solo-then-later-multiplied PNR, or an assignment made before this attribution existed) is dropped from **both** sides, same as before per-passenger seat attribution existed at all - there's no way to know whose it was. Copied to the new PNR (not moved): `segments`/`phones`/`receivedFrom`/`remarks`/`osis`/`ssrs`/`formOfPayment`/`ticketing` — real Sabre divide keeps the itinerary in both resulting PNRs. Each copied segment's own `seats` *count* (the integer that prints as `HK{n}`/`HL{n}` and that `priceItinerary` multiplies the per-seat fare by) is **not** just copied verbatim either: it's rescaled on both sides to that side's own post-divide headcount (moved-passenger count on the new PNR, remaining-passenger count on the original) — otherwise a later `WP` on either resulting PNR would silently re-price for the original combined party instead of its own, smaller one, and the segment display would keep showing the pre-divide count. Both PNRs get `pricing`/`tickets` invalidated (party size changed on both sides); the new PNR is saved into `state.history` immediately under a fresh `genLocator()`, while the original keeps its own locator but isn't auto-resaved — same as any other work-area edit, it needs another `ER`.

- **Fare-shop (`FQ{ORIG}{DEST}`, `fareQuoteShop`)** — real Sabre's bare fare quote by city pair, independent of any PNR/itinerary, unlike `WP` which requires an already-sold segment. Seeds off the route only (`hashStr('FQ'+orig+dest)`) and reuses the same shared `FARE_FORMULA`/`CLASS_FARE_MULT`/`TAX_POOL` constants `priceItinerary` reads, via its own small parallel calculation (one indicative total per booking class, since there's no real segment to price) — same "shared numbers, separate per-edition algorithm" precedent as `priceItinerary` itself. Purely informational: no PNR mutation, no activity log entry, matching `DC`/`DAN`'s existing precedent as pure lookups.

- **Fuller fare rules (`spec/reference-data.json`'s `fareRules`, `fareRulesLines`/`_fare_rules_lines`)** — each booking class's rule set grew from three fields (change fee, refundable, advance purchase) to six: `cancellationFee` (a separate, often-lower fee than the change fee, charged even on a nominally "refundable" fare — real fares frequently distinguish the two) and `minStayDays`/`maxStayDays` (a Saturday-night-stay-style minimum and a validity-window maximum, the classic deep-discount-fare restrictions this simulator had no data for at all before). `fareRulesLines`/`_fare_rules_lines` is a small shared helper (used by both `fareQuoteShop`'s `/{CLASS}` rule view and `priceItinerary`'s post-total FARE RULES block, so the two can't drift on which fields they show) that renders cancellation fee as `N/A - NONREFUNDABLE` rather than a misleading dollar figure when the fare isn't refundable to begin with, and minimum stay as `NONE` rather than `0 NIGHTS`. Min/max stay are **informational only** — same "no booking-time enforcement" precedent already established for baggage allowance, since this app doesn't model return-trip stay-duration checking against actual booked dates. Cancellation fee is the one field that became real behavior, not just display: `refundTickets`/`refund_tickets` (`TKTR`) now deducts it (floored at 0) from the refunded `pricing.total` and reports the deduction, instead of always refunding the fare in full once a fare was merely refundable at all.

- **Flexible-date availability (`AF{DD}{MMM}{ORIG}{DEST}`, `genFlexibleAvailability`/`gen_flexible_availability`)** — real-world fare shopping is rarely pinned to one exact date; this answers "which nearby day is cheapest" the way a consumer flight-search fare calendar does, before committing to a specific `A`/`1` search. Modeled on `S{DDMMM}{ORIG}{DEST}` schedule display's "same shape, different letter" precedent (`AF` instead of `A`/`1`/`S` — no grammar collision, since `availability_a`'s pattern requires a digit immediately after `A`), showing a 7-date window (queried date ±3 days) rather than schedule's forward-only 7 days, since the point here is "nearby alternatives" rather than "what's coming up." Deliberately reuses `genAvailability`'s exact per-date seed (`hashStr(orig+dest+day+mon+year)`) for each date, same "one underlying schedule, different view" precedent `genSchedule` already established — a date in this window that's also directly searched shows the literal same flights. Nonstop only, like schedule (connections are a booking-time concept). Each date's one-line fare estimate (cheapest class with `seats > 0`, or `SOLD OUT`) continues drawing from that date's own local RNG instance — discarded right after that date's loop iteration — rather than a separate stream, so, like the codeshare feature above, this can't perturb any other generated value. Purely a read-only, non-bookable lookup like `DC`/`DAN`/`FQ`: no PNR interaction, no completeness rule, explicit "not bookable directly" disclaimer pointing back to `A`.

- **Schedule change (`applyScheduleChanges`, inside `endTransaction`)** — real airline schedule changes are airline-initiated, not something an agent types; the honest equivalent here is a one-time, deterministic seeded check per segment, run every time a PNR is saved (`ER`/`ET`). The seed (`spec/reference-data.json`'s `scheduleChange`: `chance`/`minShiftMinutes`/`maxShiftMinutes`) is built from flight+route+date identity only — deliberately **not** the PNR's `locator` (which is genuinely random, from `Math.random()`/`random.choice`, not the seeded PRNG) — so the same flight always gives the same outcome regardless of which PNR it's booked on, matching real life (a schedule change hits a flight, not one lucky/unlucky booking) and keeping it reproducible instead of flaking per test run. A segment's own `scheduleChanged` flag (not the seed) is what stops it from re-rolling on a later save of that same segment. On a hit, `dep`/`arr` shift together (a time change, not a duration change) and `pricing`/`tickets` are silently cleared (no dedicated print) and the locator is auto-queued to queue `"1"` (`SCHEDULE CHANGE` — already defined in `queueCategories` but unused before this). There's no new discovery command: it surfaces entirely through channels that already exist — `QC`/`QN1`, or the alert `refreshAndPrintPNR`/`refresh_and_print_pnr` prints whenever a redisplay (`ER`'s own, `*R`, or after `QN1`) shows an unpriced PNR with a changed segment. That alert naturally stops once the agent re-`WP`s (reusing the existing pricing-null-means-stale convention rather than a separate acknowledgement flag) — `ET`'s redisplay is skipped (work area cleared instead), so `ET` alone doesn't reveal a same-call change; a later `*{LOCATOR}`/`QN1` does. Known simplification: `dep`/`arr` are plain minute offsets everywhere in this app, relative to the segment's own `dinfo` date — a shift doesn't roll `dinfo` itself to a different calendar day, even if the shifted `dep` technically crosses midnight (rare: would need a large shift against an already-early departure). This does **not** affect the arrival-day display below, since that's computed as a relative diff between `dep` and `arr` regardless of either's absolute value.

- **Waitlist clearing (`applyWaitlistClearing`, inside `endTransaction`)** — the same deterministic-seeded-check-at-save-time mechanism as schedule change above, for `queueCategories["18"]` (`WAITLIST CLEARED` — also predated this session, also unused before it). Three deltas from schedule change: (1) it flips a segment's `status` from `HL` to `HK` instead of shifting `dep`/`arr` — same flight/class/fare, not an itinerary change, so `pricing`/`tickets` are never touched (no `clearPricingAndTickets` call); (2) the seed folds in `cls` too (`hashStr('WLCLEAR'+...)`, vs. schedule change's `'SKEDCHG'` prefix — distinct prefixes so the two features' seeds can't collide for the same flight+date), since waitlist status is class-specific, not just flight-specific; (3) no `scheduleChanged`-style flag is needed to gate the roll — only segments currently `HL` are ever considered, and a cleared segment becomes `HK` immediately, so it naturally drops out on the next check. The discovery alert is deliberately **show-once, not show-until-resolved**: clearing a waitlist needs no follow-up action (unlike a schedule change, which needs a re-price), so nagging on every redisplay forever would be wrong. `waitlistCleared` (permanent fact) and `waitlistClearAcked` (starts `false`) drive this — `refreshAndPrintPNR`/`refresh_and_print_pnr` prints the notice for any segment with `waitlistCleared && !waitlistClearAcked` and sets `waitlistClearAcked = true` for those segments as part of that same print pass, a deliberate small mutation inside the display path so the notice surfaces exactly once (typically on `ER`'s own redisplay, or a later `QN18`/`*{LOCATOR}`) and never repeats.

- **Form of payment (`FPCASH`/`FPCHECK`/`FPCC...`, `state.pnr.formOfPayment`)** — required by `endTransaction` just like the fare quote and ticketing arrangement, matching real Sabre where a PNR can't be ticketed without one. Credit card numbers are masked to their last 4 digits (`maskCard`) before being stored/displayed — never keep the full number around, even in this synthetic training context.

- **PNR activity history (`state.pnr.activityLog`, `logActivity`, `*H`)** — a chronological, timestamped+sine-stamped log distinct from `state.history` (which only holds locator → full-PNR snapshots). `logActivity()` is called alongside nearly every mutating confirmation message (sell, name, price, phone, RF, FP, ticketing, SSR/OSI, seat assign, cancel, save, retrieve) so `*H` reflects the real sequence of actions on the PNR, not just its current state. The log travels with the PNR through `JSON.parse(JSON.stringify(...))` clones on save/retrieve, so history persists across `ER`/`*{LOCATOR}` cycles the same way a real Sabre PNR's history does.
