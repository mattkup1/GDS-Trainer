# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

**GDS Trainer** — a GDS (Global Distribution System) terminal simulator branded independently of any real GDS vendor, plain HTML/CSS/JS split across `index.html` (markup), `style.css` (CRT/terminal styling), and `script.js` (all logic). It emulates the classic green-phosphor CRT terminal and industry-standard GDS entry mnemonics — historically associated with systems like Sabre — for training/educational purposes (sign-in, availability, sell, PNR build, end transaction). All flight/availability data is synthetic, generated by a seeded PRNG — there are no network calls or external dependencies anywhere in the app. There is also a Python terminal (CLI) edition, `gds-trainer-cli/`, implementing the same command grammar and business rules independently.

Note: code comments and inline documentation below still refer to "Sabre" where they describe the real-world entry conventions this simulator is modeled on (e.g. "matches real Sabre's ticketing gate") — that's accurate engineering context, not product branding. The product's own name, UI text, and packaging use "GDS Trainer" throughout; see `productization-gtm-memo.html` for the rationale.

`GDS-TRAINER-BOOKING-GUIDE.pdf` is a printable version of the same walkthrough as `HOW-TO-BOOK-A-FLIGHT.md`, generated from `GDS-TRAINER-BOOKING-GUIDE.html` (kept in the repo as the editable source — the PDF itself is a build artifact, not hand-edited). To update the guide: edit the `.md` walkthrough first, port the same changes into the `.html`, then regenerate the PDF with headless Chrome:

```bash
"/Applications/Google Chrome.app/Contents/MacOS/Google Chrome" \
  --headless --disable-gpu --no-pdf-header-footer \
  --print-to-pdf="GDS-TRAINER-BOOKING-GUIDE.pdf" --print-to-pdf-no-header \
  "file://$(pwd)/GDS-TRAINER-BOOKING-GUIDE.html"
```

`HOW-TO-BOOK-A-FLIGHT.md` is the companion user-facing walkthrough (step-by-step booking flow with the exact commands to type).

## Running it

There is no build step, package manager, or test suite — these are static files loaded via plain `<link>`/`<script src>` tags (not ES modules), so `index.html` can be opened directly via `file://` with no local server needed.

## Architecture (`script.js`)

Everything lives in one IIFE. Key pieces:

- **`state`** — the whole app's runtime state: `signedIn`/`sine`/`pcc`, `pnr` (the in-progress booking), `lastAvail` (most recent availability search results), `lastDisplay` (numbered element list from the last PNR render), `history` (saved PNRs keyed by record locator), and `cmdHistory` (for arrow-key recall in the input).

- **`processCommand(raw)`** — the command dispatcher. Uppercases input and matches it against an ordered list of regexes/literals that mimic real Sabre entry syntax: `SI`/`SO` (sign in/out), `A{DD}{MON}{ORIG}{DEST}` / `1{DD}{MON}{ORIG}{DEST}` (availability — both are authentic Sabre entries), `0{LINE}{CLASS}{SEATS}` (sell from availability), `0{AL}{FLT}{CLASS}{DD}{MON}{ORIG}{DEST}{STATUS}{SEATS}` (long/direct sell — real Sabre prefixes this with `0`, not `SS`, which is an Apollo/Worldspan convention), `-SURNAME/GIVEN` and `-{N}SURNAME/GIVEN1 TITLE1/GIVEN2 TITLE2` (name, incl. multiple same-surname passengers in one entry, plus an optional trailing `(INF{SURNAME}/{GIVEN}/{DOB})` suffix to attach a lap infant to the passenger just added), `9{NUMBER}-{LOC}` / `9/{CITY}{NUMBER}-{LOC}` (phone), `6{TEXT}` (received-from — real Sabre uses the digit `6`, not `P`), `WP`/`WPNCS` (price itinerary — required before ticketing), `7TAW/` / `7TAW{date}/{time}` / `7TAX{date}/{time}` (ticketing arrangement/time limit), `FPCASH`/`FPCHECK`/`FPCC{TYPE}{CARDNUM}/{MMYY}` (form of payment — required before end transaction, mirroring real Sabre's ticketing gate), `TKTT` (issue ticket numbers — distinct from the ticketing *arrangement* above; see the dedicated bullet below), `3{SSRCODE}[-{PAX}][/{TEXT}]` (special service request, validated against the `SSR_CODES` table), `3OSI{AL}{TEXT}` (other service info), and `3FQTV{AL}{NUMBER}` (frequent flyer number, stored as an SSR) — the latter two are checked *before* the general SSR pattern since both would otherwise also satisfy its 4-letter-code shape, `4{N}` (seat map for itinerary segment N) and `4{N}-{SEAT}` (assign a seat — hyphen-delimited to avoid ambiguity between a multi-digit segment number and a multi-digit seat row), `DC{CODE}` / `DAN{TEXT}` (decode an airport code / search airports by name, both against the `AIRPORTS` table), `*R`/`*`/`*H`/`*{LOCATOR}` (display current PNR / activity history / retrieve by locator), `X{N}` / `X{N}-{M}` / `X{N},{M}` (cancel element(s)), `XI` (cancel entire itinerary), `IG`/`ER`/`ET` (ignore/end transaction). Order matters here since several patterns are single-character-prefixed and could otherwise collide — check existing branch ordering before adding new commands.

- **Pricing (`priceItinerary` / `WP` / `WPNCS`)** — mimics Sabre's fare-quote entry. Requires at least one segment and one name on the PNR; deterministically derives a base fare (seeded by segment details, same seeding pattern as `genAvailability`), a handful of itemized taxes, and a total, then stores it on `state.pnr.pricing`. Selling or cancelling a segment invalidates any stored price (`invalidatePricing`/`removeElement`), matching real Sabre where itinerary changes stale out a fare quote — it must be re-priced with `WP` before ticketing. `endTransaction` treats a missing `p.pricing` as an incomplete-PNR error, same as a missing name or ticketing arrangement.

- **Availability generation (`genAvailability`)** — flight data is deterministically pseudo-random: `hashStr()` seeds `mulberry32()` from the route+date string, so the same query always returns the same flights. There is no real airline/schedule data source; adding one would mean replacing this function's internals, not the dispatcher.

- **PNR element model (`buildElements` / `refreshAndPrintPNR` / `cancelElements`)** — names, infants, segments, seats, SSRs, OSIs, pricing, phones, receivedFrom, and ticketing are stored on `state.pnr` (names/segments/phones/infants/seats/ssrs/osis as arrays, the rest as single values), but flattened into a single numbered list every time the PNR is displayed. `state.lastDisplay` holds that numbering, and `X{n}` (or a range/list of `n`s, or `XI` for the whole itinerary) cancellation looks up the array/index each number points to — so cancellation only works correctly against the most recently displayed numbering, not stale state. Multi-element cancels process highest-numbered element first so earlier splices don't shift the indices of elements still queued for removal. Seats are linked to segments by array index (`seat.segIdx`); cancelling a segment (`removeElement`'s `'segment'` branch, and `cancelItinerary` for `XI`) drops that segment's seats and reindexes the rest so they still point at the correct remaining segment.

- **Seat maps (`getSeatMap` / `showSeatMap` / `assignSeat`)** — like availability and pricing, the occupied/open grid is deterministic: seeded by the segment's flight+date+route, so `4{N}` always regenerates the same 30-row, 6-column (A–F) layout for that segment. Assignments are only checked against this generated grid and the PNR's own `state.pnr.seats`, not against other passengers' bookings (there's no shared inventory across simulated PNRs).

- **Special service requests / OSI (`SSR_CODES`, the `3...` dispatcher branches)** — SSR codes are validated against a fixed lookup table (meal requests, wheelchair, unaccompanied minor, etc.); unrecognized 4-letter codes after `3` are rejected rather than silently accepted. `3OSI{AL}{TEXT}` is checked ahead of the general `3{CODE}` pattern since `OSI` would otherwise also satisfy the 4-letter-code shape.

- **End transaction (`endTransaction`)** — validates the PNR is complete (segment, name, fare quote, phone, received-from, form of payment, ticketing all present) before generating a 6-character record locator via `genLocator()` and saving into `state.history`. `ER` keeps the PNR loaded and redisplays it; `ET` clears the work area for the next booking. Both behaviors matter for training accuracy — don't collapse them into one.

- **Ticketing (`TKTT`, `issueTickets`)** — deliberately kept separate from `endTransaction`/completeness, matching real Sabre: a PNR can be saved (`ER`/`ET`) without being ticketed (deferred ticketing via a time limit is normal), and the `7TAW/`/`7TAX...` "ticketing arrangement" only sets a deadline — it doesn't ticket anything. `TKTT` is the actual ticket-issuance entry; it requires the PNR to already have a locator (i.e. already end-transacted once), a fare quote, a ticketing arrangement, and a form of payment, and refuses to double-ticket an already-ticketed PNR. It generates one ticket number per name (plus one per infant) using a real-world IATA airline numeric code (`AIRLINE_NUMERIC_CODES`) for the first segment's carrier as validating carrier, deterministically seeded by locator+passenger like the rest of the app's synthetic data. `invalidatePricing()` — already called whenever a segment is sold — also voids any issued tickets and announces it, and the segment/fare-quote cancellation paths in `removeElement`/`cancelItinerary` silently clear `state.pnr.tickets` the same way they silently null `pricing`, so a ticketed PNR whose itinerary changes always needs `WP` then `TKTT` again before it can be re-saved as ticketed.

- **Form of payment (`FPCASH`/`FPCHECK`/`FPCC...`, `state.pnr.formOfPayment`)** — required by `endTransaction` just like the fare quote and ticketing arrangement, matching real Sabre where a PNR can't be ticketed without one. Credit card numbers are masked to their last 4 digits (`maskCard`) before being stored/displayed — never keep the full number around, even in this synthetic training context.

- **PNR activity history (`state.pnr.activityLog`, `logActivity`, `*H`)** — a chronological, timestamped+sine-stamped log distinct from `state.history` (which only holds locator → full-PNR snapshots). `logActivity()` is called alongside nearly every mutating confirmation message (sell, name, price, phone, RF, FP, ticketing, SSR/OSI, seat assign, cancel, save, retrieve) so `*H` reflects the real sequence of actions on the PNR, not just its current state. The log travels with the PNR through `JSON.parse(JSON.stringify(...))` clones on save/retrieve, so history persists across `ER`/`*{LOCATOR}` cycles the same way a real Sabre PNR's history does.
