# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A Sabre GDS (Global Distribution System) terminal simulator — plain HTML/CSS/JS split across `index.html` (markup), `style.css` (CRT/terminal styling), and `script.js` (all logic). It emulates the classic green-phosphor CRT terminal and Sabre entry mnemonics (sign-in, availability, sell, PNR build, end transaction) for training/educational purposes. All flight/availability data is synthetic, generated by a seeded PRNG — there are no network calls or external dependencies anywhere in the app.

`HOW-TO-BOOK-A-FLIGHT.md` is the companion user-facing walkthrough (step-by-step booking flow with the exact commands to type).

## Running it

There is no build step, package manager, or test suite — these are static files loaded via plain `<link>`/`<script src>` tags (not ES modules), so `index.html` can be opened directly via `file://` with no local server needed.

## Architecture (`script.js`)

Everything lives in one IIFE. Key pieces:

- **`state`** — the whole app's runtime state: `signedIn`/`sine`/`pcc`, `pnr` (the in-progress booking), `lastAvail` (most recent availability search results), `lastDisplay` (numbered element list from the last PNR render), `history` (saved PNRs keyed by record locator), and `cmdHistory` (for arrow-key recall in the input).

- **`processCommand(raw)`** — the command dispatcher. Uppercases input and matches it against an ordered list of regexes/literals that mimic real Sabre entry syntax: `SI`/`SO` (sign in/out), `A{DD}{MON}{ORIG}{DEST}` / `1{DD}{MON}{ORIG}{DEST}` (availability — both are authentic Sabre entries), `0{LINE}{CLASS}{SEATS}` (sell from availability), `0{AL}{FLT}{CLASS}{DD}{MON}{ORIG}{DEST}{STATUS}{SEATS}` (long/direct sell — real Sabre prefixes this with `0`, not `SS`, which is an Apollo/Worldspan convention), `-SURNAME/GIVEN` and `-{N}SURNAME/GIVEN1 TITLE1/GIVEN2 TITLE2` (name, incl. multiple same-surname passengers in one entry), `9{NUMBER}-{LOC}` / `9/{CITY}{NUMBER}-{LOC}` (phone), `6{TEXT}` (received-from — real Sabre uses the digit `6`, not `P`), `WP`/`WPNCS` (price itinerary — required before ticketing), `7TAW/` / `7TAW{date}/{time}` / `7TAX{date}/{time}` (ticketing arrangement/time limit), `*R`/`*`/`*{LOCATOR}` (display/retrieve PNR), `X{N}` / `X{N}-{M}` / `X{N},{M}` (cancel element(s)), `XI` (cancel entire itinerary), `IG`/`ER`/`ET` (ignore/end transaction). Order matters here since several patterns are single-character-prefixed and could otherwise collide — check existing branch ordering before adding new commands.

- **Pricing (`priceItinerary` / `WP` / `WPNCS`)** — mimics Sabre's fare-quote entry. Requires at least one segment and one name on the PNR; deterministically derives a base fare (seeded by segment details, same seeding pattern as `genAvailability`), a handful of itemized taxes, and a total, then stores it on `state.pnr.pricing`. Selling or cancelling a segment invalidates any stored price (`invalidatePricing`/`removeElement`), matching real Sabre where itinerary changes stale out a fare quote — it must be re-priced with `WP` before ticketing. `endTransaction` treats a missing `p.pricing` as an incomplete-PNR error, same as a missing name or ticketing arrangement.

- **Availability generation (`genAvailability`)** — flight data is deterministically pseudo-random: `hashStr()` seeds `mulberry32()` from the route+date string, so the same query always returns the same flights. There is no real airline/schedule data source; adding one would mean replacing this function's internals, not the dispatcher.

- **PNR element model (`buildElements` / `refreshAndPrintPNR` / `cancelElements`)** — names, segments, pricing, phones, receivedFrom, and ticketing are stored on `state.pnr` (names/segments/phones as arrays, the rest as single values), but flattened into a single numbered list every time the PNR is displayed. `state.lastDisplay` holds that numbering, and `X{n}` (or a range/list of `n`s, or `XI` for the whole itinerary) cancellation looks up the array/index each number points to — so cancellation only works correctly against the most recently displayed numbering, not stale state. Multi-element cancels process highest-numbered element first so earlier splices don't shift the indices of elements still queued for removal.

- **End transaction (`endTransaction`)** — validates the PNR is complete (segment, name, phone, received-from, ticketing all present) before generating a 6-character record locator via `genLocator()` and saving into `state.history`. `ER` keeps the PNR loaded and redisplays it; `ET` clears the work area for the next booking. Both behaviors matter for training accuracy — don't collapse them into one.
