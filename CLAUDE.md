# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A Sabre GDS (Global Distribution System) terminal simulator — plain HTML/CSS/JS split across `index.html` (markup), `style.css` (CRT/terminal styling), and `script.js` (all logic). It emulates the classic green-phosphor CRT terminal and Sabre entry mnemonics (sign-in, availability, sell, PNR build, end transaction) for training/educational purposes. All flight/availability data is synthetic, generated by a seeded PRNG — there are no network calls or external dependencies anywhere in the app.

`HOW-TO-BOOK-A-FLIGHT.md` is the companion user-facing walkthrough (step-by-step booking flow with the exact commands to type).

## Running it

There is no build step, package manager, or test suite — these are static files loaded via plain `<link>`/`<script src>` tags (not ES modules), so `index.html` can be opened directly via `file://` with no local server needed.

## Architecture (`script.js`)

Everything lives in one IIFE. Key pieces:

- **`state`** — the whole app's runtime state: `signedIn`/`sine`/`pcc`, `pnr` (the in-progress booking), `lastAvail` (most recent availability search results), `lastDisplay` (numbered element list from the last PNR render), `history` (saved PNRs keyed by record locator), and `cmdHistory` (for arrow-key recall in the input).

- **`processCommand(raw)`** — the command dispatcher. Uppercases input and matches it against an ordered list of regexes/literals that mimic real Sabre entry syntax: `SI`/`SO` (sign in/out), `A{DD}{MON}{ORIG}{DEST}` (availability), `0{LINE}{CLASS}{SEATS}` (sell from availability), `SS...` (direct sell), `-SURNAME/GIVEN` (name), `9...` (phone), `P...` (received-from), `TAW/` / `TAU{date}/{time}` (ticketing), `*R`/`*`/`*{LOCATOR}` (display/retrieve PNR), `X{N}` (cancel element), `IG`/`ER`/`ET` (ignore/end transaction). Order matters here since several patterns are single-character-prefixed and could otherwise collide — check existing branch ordering before adding new commands.

- **Availability generation (`genAvailability`)** — flight data is deterministically pseudo-random: `hashStr()` seeds `mulberry32()` from the route+date string, so the same query always returns the same flights. There is no real airline/schedule data source; adding one would mean replacing this function's internals, not the dispatcher.

- **PNR element model (`buildElements` / `refreshAndPrintPNR` / `cancelElement`)** — names, segments, phones, receivedFrom, and ticketing are stored in separate arrays on `state.pnr`, but flattened into a single numbered list every time the PNR is displayed. `state.lastDisplay` holds that numbering, and `X{n}` cancellation looks up the array/index it points to — so cancellation only works correctly against the most recently displayed numbering, not stale state.

- **End transaction (`endTransaction`)** — validates the PNR is complete (segment, name, phone, received-from, ticketing all present) before generating a 6-character record locator via `genLocator()` and saving into `state.history`. `ER` keeps the PNR loaded and redisplays it; `ET` clears the work area for the next booking. Both behaviors matter for training accuracy — don't collapse them into one.
